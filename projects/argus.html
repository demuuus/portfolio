Argus

Overview

Argus is a self-hosted, AI-assisted vulnerability management platform. It tracks an organisation's asset inventory, matches each asset against the National Vulnerability Database, enriches findings with exploit intelligence, and ranks them by a calculated risk score. Everything is available through a Flask web dashboard and a Telegram bot that share one PostgreSQL database.

The name comes from Argus Panoptes, the hundred-eyed giant of Greek mythology who never fully slept. Like its namesake, Argus keeps watching assets around the clock and raises an alert when something needs attention.

Problem

Small security teams and individual analysts often have the raw ingredients for vulnerability management, an asset list and access to public CVE feeds, but not the tooling to connect them. Finding out what affects them, which vulnerabilities are actually being exploited, and what to fix first usually means cross-referencing spreadsheets by hand.

Solution

Argus automates that correlation loop. Assets are scanned daily against the NVD, every finding is checked against CISA's Known Exploited Vulnerabilities catalogue and FIRST's EPSS exploit-probability scores, and a deterministic formula turns those signals into one risk score per finding:

Risk = (CVSS × 10) + (EPSS percentile × 1000) + criticality bonus + KEV bonus

On top of this pipeline sits an AI Security Copilot. Every answer is built from live database queries rather than the model's training memory, so responses reflect the current state of the environment.

Key Features

  • Asset inventory with vendor, product, version, type, location, owner, and criticality
  • NVD integration with CVSS fallback from v3.1 to v3.0 to v2, plus CISA KEV and EPSS enrichment
  • Deduplicated findings with an open, resolved, and patched workflow and owner assignment
  • AI chat that routes each question by intent and grounds its answer in live PostgreSQL data
  • Automatic AI analysis of every newly discovered CVE, with retries and a watchdog for stuck jobs
  • Daily, weekly, monthly, and yearly PDF reports, generated on schedule or on demand
  • Telegram bot for adding assets, running scans, reviewing findings, and receiving batched alerts
  • Dashboard charts for risk distribution, KEV exposure, vendor breakdown, and findings history

Architecture

The web dashboard and the Telegram bot run as independent processes but call into the same Python modules for database access, scanning, risk scoring, reporting, and AI, so no logic is duplicated between them. APScheduler drives the background jobs: the daily scan, risk snapshots for trend charts, scheduled reports, and the AI analysis queue. The AI layer talks to any OpenAI-compatible endpoint and was evaluated against a local llama.cpp server, so vulnerability data never has to leave the machine.

Security by Design

  • The app refuses to start without an explicit secret key and admin credentials, with no insecure fallback
  • Role-based access with admin and viewer roles, enforced at the route level
  • CSRF protection on every state-changing route and hashed passwords
  • HTTP-only, SameSite session cookies with a fixed session lifetime

Technical Challenges

Keeping AI answers trustworthy was the central challenge. Instead of letting the model answer from memory, the copilot classifies each question, runs the matching set of queries, and passes only that structured context to the model. Responses are cached against a hash of both the question and the live data, so a cached answer is invalidated automatically the moment the underlying findings change.

The database also had to stay consistent across many iterations. The schema is self-healing: migrations are idempotent and applied at startup, so the same codebase can run on a fresh or an existing database without manual steps.

What I Learned

Argus taught me how vulnerability management works in practice, from CVSS, KEV, and EPSS to why a severity score alone is not enough to prioritise. On the engineering side, it showed me how to share one data layer between two interfaces, how to run reliable background jobs, and how to put an LLM to work responsibly by grounding it in real data and being explicit about its limits.
